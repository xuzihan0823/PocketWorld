# 项目文档维护

借鉴 planning-with-files 的文件持久化、恢复上下文、阶段核对和单一负责人机制，让项目约定随代码保持准确。沿用项目已有的任务计划、模块进度和 PR 流程。

## 识别与适配项目

以用户指定的目标项目或当前任务工作区为根目录。安装目录仅存放本技能及参考资料，项目文档写入目标项目。

首次使用时，读取适用的 `AGENTS.md`、`AGENT.md`、README、文档索引和 PR 模板，再按任务范围查找产品规范、模块说明、公共类型、协议或 schema、现有计划和相关决策记录。识别每类信息的维护位置、负责人和当前任务的分支或 PR。接续任务优先恢复已有记录。

发现 PocketWorld 项目时，按需读取本技能的 [PocketWorld 适配说明](references/pocketworld.md)。用仓库身份、README 和入口代码确认项目，参考文件中的路径作为查找线索。

已有文件能承担职责时直接复用，保留目录边界、字段和工作流。多任务并行时绑定当前任务的工作区、分支及计划标识，共享文档在各自分支提出修改，由维护负责人协调审查。已有 planning-with-files 计划按该技能的选择规则恢复。

涉及本地开发或提交交付时，读取 [开发与交付流程](references/delivery-workflow.md)，落实任务分支、独立工作区、提交检查、尽早推送与草稿 PR、迭代和合并后清理。PocketWorld 的依赖复用、预览与验证细节见 [本地开发流程](references/pocketworld-local-dev.md)。

用户要求定期维护或配置 hooks 时，读取 [四种宿主的 hooks](references/hooks.md)。已收到维护提醒时，先核对实际文档与原 PR，再用提示中的会话标识记录核对结果和证据。

用户要求初始化维护机制时，把信息归属、维护责任、更新触发条件和交付检查写入现有协作规范，补充必要索引及 PR 检查项。缺少文档时只创建当前范围需要的部分。用户仅要求讨论或检查时，先给出适配判断和建议。

## 信息归属

| 信息 | 主要维护位置 |
| --- | --- |
| 分工、修改边界、审查和验证流程 | 协作规范 |
| 用户可见功能、操作流程、状态反馈和验收条件 | 产品规范 |
| 参数、回调、事件和数据结构 | 公共类型、协议或 schema |
| 模块调用顺序、状态归属、资源生命周期、失败与恢复行为 | 跨模块交互契约 |
| 重大设计的原因、取舍、影响和替代关系 | 已有设计决策记录或提案 |
| 当前任务目标、待办、阻塞和验证结果 | 当前任务的计划或 PR |
| 模块整体的当前能力和已知限制 | 已有模块进度文档 |

同一事实指定一个主要维护位置，其他文档通过链接引用。公共接口链接到代码定义，交互契约补充类型无法表达的行为要求。历史过程由 Git、PR 和决策记录追溯，当前说明持续整理为最新状态。

## 跟随变更维护

### 开始任务

读相关约定和真实入口，检查接口调用方、实现方、状态存储及现有验证。明确目标、依赖模块、已有行为、维护责任和待确认问题。任务进度使用仓库已有载体，公共约定由一名维护负责人协调，参与者更新自己的任务记录。

### 作出决策

跨模块调用、状态归属、共享输入、数据格式或资源生命周期发生变化时，先核对受影响方。将方案、影响和兼容处理写入当前任务的设计或 PR，按项目规则取得相关维护者确认。区分待讨论、已确认待实施和已合并行为。

代码与已确认规范存在差异时，记录具体差异和证据，按当前任务授权修复代码或提出规范调整。把未决问题交给有权限的维护者裁定。

### 完成阶段

在同一个 PR 中提交代码及相关规范或契约更新。进度记录同步当前阶段、下一步、阻塞和实际验证结果。未影响约定的内部调整可以在 PR 中说明已核对及理由。

只有影响较大的跨模块设计需要单独决策记录，普通修复沿用常规 PR。每条约定写入足够指导接入和验收的信息，按任务范围控制文档数量与篇幅。

### 提交交付

- 核对描述与当前变更一致，链接指向有效文件，新增或移动文件的引用已同步。
- 检查调用方与实现方兼容，状态、输入、音频、监听、计时和持久化责任有明确归属。
- 记录实际执行的检查、结果与未验证项。文档格式检查只证明结构，行为结论需要相应证据。
- 在 PR 中链接已核对或更新的文档，说明集成影响、待协调事项和维护负责人。纯文档改动按仓库规则检查差异、链接与结构。

## 交互契约的最小内容

沿用项目已有模板。新建时覆盖以下内容即可，按模块风险增减。

- 范围、维护负责人、提供方与使用方。
- 当前状态及公共接口、实现入口的链接。
- 触发条件、调用顺序和状态变化，必要时附简短时序图。
- 状态和数据由谁维护，事件或回调由谁发起和消费。
- 暂停、取消、退出、失败与重试时，各方如何清理或恢复。
- 兼容约束、旧数据处理及受影响的模块。
- 验收场景、现有检查入口和待确认事项。

## 使用方式与边界

安装提供技能、参考资料、检查脚本与宿主适配器。hooks 经过注册、信任和宿主加载后触发检查，具体步骤与能力边界见 hooks 参考。通过普通任务请求也可执行维护。

维护文档遵循目标仓库的权限和提交规则。安装技能本身只完成分发，初始化或修改项目规范需要相应任务授权。
